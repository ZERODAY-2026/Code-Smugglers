DATAMIND - JUDGE PRESENTATION PREPARATION
=========================================

This file is for local preparation only. It is intentionally not being added
to GitHub.


1. ONE-MINUTE PROJECT SUMMARY
-----------------------------

DataMind is an evidence-backed natural-language analytics application.

Instead of forcing a user to write SQL, the user asks a question in plain
English. Google Gemma interprets the question using the real Snowflake schema
and produces a structured query plan. The backend validates the generated SQL,
executes only approved read-only queries in Snowflake, and returns the actual
rows, SQL, explanation, assumptions, warnings, and Snowflake query ID.

The frontend presents the evidence in a simple liquid-glass interface. It
shows the result table first and adds an optional chart only when the returned
data is appropriate for visualization. It does not fabricate numbers or
replace the evidence table with a chart.

Short pitch:

"DataMind turns natural-language questions into safe, schema-grounded
Snowflake analytics and shows the answer together with inspectable evidence."


2. PROBLEM STATEMENT
--------------------

Many people have useful data but cannot easily query it because SQL requires
technical knowledge. Existing dashboards are often static, require developers
to create every view manually, or hide how the result was calculated.

The problem DataMind solves is:

How can a user ask questions about a dataset in natural language and receive
an understandable answer that is dynamically computed, safe, inspectable,
and supported by real database evidence?

The important requirements are:

- Accept natural-language questions.
- Use the real dataset schema rather than guessing columns.
- Generate SQL with an AI planner.
- Execute the query against Snowflake.
- Prevent unsafe or unauthorized SQL.
- Show the actual SQL and returned rows.
- Explain assumptions and warnings.
- Handle ambiguity, unsupported questions, empty results, and failures
  honestly.
- Support more than one configured dataset.
- Make the result understandable to both technical and non-technical users.

6. HOW THE APPLICATION WORKS
----------------------------

The end-to-end flow is:

1. The browser loads the React application.
2. The frontend calls:
   - GET /health
   - GET /api/schema
3. The backend checks the configured dataset and discovers the real schema
   from Snowflake.
4. The user asks a question in plain English.
5. The frontend sends:

   POST /api/query
   {
     "question": "Show the average balance by education."
   }

6. The backend obtains the active schema and sends the question plus schema
   context to Gemma.
7. Gemma returns a structured plan containing a status, SQL, explanation,
   assumptions, and warnings.
8. The backend checks the plan:
   - Is it valid structured output?
   - Is it supported?
   - Does it need clarification?
   - Does it contain SQL?
9. If SQL exists, SQLGlot parses and validates it.
10. The backend permits only one read-only SELECT-style query.
11. The backend checks that every table is fully qualified and belongs to the
    active dataset allowlist.
12. The approved SQL executes in Snowflake.
13. Snowflake returns columns, rows, and a query ID.
14. The backend packages the real evidence into a response.
15. The frontend displays:
    - Status
    - Answer or clarification
    - Explanation
    - Result table
    - Optional generated SQL
    - Assumptions
    - Warnings
    - Snowflake query ID
16. If the result has a suitable two-column numeric/category shape, the
    frontend adds a simple bar or pie chart. The table remains the primary
    evidence.

Pipeline:

Natural language
    -> schema context
    -> Gemma structured plan
    -> SQL validation
    -> Snowflake execution
    -> evidence response
    -> table plus optional visualization


7. WHAT IS GEMMA?
-----------------

Gemma is Google's family of open-weight generative AI models. It can
understand natural language and generate structured outputs when prompted
with clear constraints.

In DataMind, Gemma is not used as a database and it is not trusted to
calculate the final answer. Its role is query planning:

- Understand the user's intent.
- Match the intent to the provided schema.
- Decide whether clarification is needed.
- Decide whether the request is unsupported.
- Generate a candidate SQL query.
- Provide an explanation, assumptions, and warnings.

The configured working model is:

    gemma-4-26b-a4b-it

The model is accessed through Google's official Google Gen AI SDK.

Important design principle:

Gemma proposes the SQL; Snowflake computes the result. This reduces the risk
of presenting an AI-generated number that was never calculated from the data.


8. WHAT IS SNOWFLAKE?
---------------------

Snowflake is a cloud data platform and analytical data warehouse. It stores
data and executes SQL at scale.

DataMind uses Snowflake for:

- Storing the configured dataset.
- Discovering tables and columns.
- Executing approved analytical SQL.
- Returning actual rows and column names.
- Providing a Snowflake query ID for traceability.

Snowflake is the source of truth for numerical results. The frontend does not
calculate counts, averages, distributions, or balances.

10. INGESTION PROCESS
---------------------

The Bank Marketing CSV is loaded through a repeatable Snowflake ingestion
script.

The process is:

1. Read the source CSV.
2. Validate the expected source structure.
3. Connect to Snowflake using configured credentials.
4. Create or use the target database and schema.
5. Create the target table with suitable column names and types.
6. Create a Snowflake stage.
7. Upload the CSV to the stage using PUT.
8. Load staged records into the table using COPY INTO.
9. Verify the loaded row count against the source data.
10. Discover the resulting schema through INFORMATION_SCHEMA.

The source field named DEFAULT is stored as DEFAULT_VALUE to avoid confusion
with SQL reserved-word behavior.

Ingestion is separate from user query execution. Normal user queries do not
upload or mutate data; they only execute approved read-only queries.


11. HOW DATA IS CLEANED AND PROCESSED
--------------------------------------

Data preparation and processing happen in controlled stages.

Source-level preparation:

- Validate that the expected CSV exists.
- Validate required columns.
- Preserve the source records.
- Normalize the target table structure.
- Use a safe name for the DEFAULT field.

Snowflake processing:

- COPY INTO loads the source records into the target table.
- SQL aggregation, filtering, grouping, and ordering are performed by
  Snowflake.
- INFORMATION_SCHEMA supplies actual column metadata.

AI planning:

- Gemma receives the schema context.
- It is instructed to use available fields instead of inventing fields.
- Structured Pydantic models validate the planner response.
- Schema pruning and SQL sanity checks reduce invalid plans.

Query safety:

- SQLGlot parses generated SQL.
- Only one statement is allowed.
- Only read-only query types are allowed.
- DML and DDL are rejected.
- Tables must be fully qualified.
- Tables must belong to the configured dataset allowlist.

Frontend processing:

- The frontend displays returned values.
- Null values are shown as an em dash rather than a fabricated value.
- The frontend formats values for readability.
- Optional charts are derived only from returned rows.
- The frontend never changes the actual database result.


12. API ENDPOINTS
-----------------

GET /health

Purpose:
Check whether the backend service is running.

Example response:

{
  "status": "ok",
  "service": "DataMind Backend"
}

GET /api/schema

Purpose:
Discover the active database, schema, dataset, tables, and columns.

Used by:

- Frontend connection status.
- Schema display.
- Planner schema context.
- Dataset-aware validation.

POST /api/query

Purpose:
Plan, validate, execute, and package a natural-language query.

Request:

{
  "question": "How many customers subscribed to a term deposit?"
}

Possible successful statuses:

- ok
- empty
- clarification_required
- unsupported

The response can contain:

- answer
- question
- sql
- columns
- rows
- explanation
- assumptions
- warnings
- query_id


13. HOW API INTEGRATION WORKS
-----------------------------

The frontend uses a shared API client. It sends JSON requests to the backend
base URL configured with:

    VITE_API_BASE_URL

For local development the default backend URL is:

    http://127.0.0.1:8000

The backend allows configured frontend origins through:

    DATAMIND_FRONTEND_ORIGINS

The browser does not receive:

- Google API keys.
- Snowflake passwords.
- Snowflake account secrets.

Those credentials stay in the backend environment.

The frontend receives only the API result payload and renders it.


14. AMBIGUOUS, UNSUPPORTED, EMPTY, AND ERROR CASES
---------------------------------------------------

Ambiguous question:

Gemma returns clarification_required. No SQL is executed.

Example:

    "Show me the performance."

Unsupported request:

Gemma returns unsupported. No SQL is executed.

Example:

    "What is the weather today?"

Valid query with no rows:

Snowflake executes the query and returns status empty. The UI says that no
matching rows were found. The SQL and query ID remain available.

Missing/null values:

Null cell values are displayed as an em dash. They are not replaced with
zero, an average, or a guessed value.

Gemma unavailable:

The backend returns HTTP 503 with a clear retry message. The frontend shows an
error and does not display fake results.

Snowflake failure:

The approved query failure is returned explicitly as a service error. The
frontend does not convert it into a successful-looking result.

Invalid or unsafe SQL:

The backend rejects it before execution.

Large result:

Results are capped at 500 rows, and a warning is included when truncation
occurs.


15. OPTIONAL VISUALIZATION DESIGN
---------------------------------

Visualization is an extra layer, not the source of truth.

The chart appears only when:

- The response status is ok.
- Exactly two columns are returned.
- One column is numeric.
- One column is categorical.
- There are between 2 and 12 usable rows.
- Category labels are unique.

Examples that can produce a chart:

- Show the distribution of customers by job.
- Show the average balance by education.
- Show the number of customers by marital status.

The table remains visible above the chart. The chart title says it is based on
returned rows. This keeps the visual simple and prevents the chart from
hiding the actual evidence.

Bar charts are used for general grouped numeric results. Pie charts are used
only for small, non-negative category distributions.


16. SECURITY AND RELIABILITY POINTS
-----------------------------------

- Secrets are kept in backend environment variables.
- The Google key is never sent to the browser.
- Snowflake credentials are never sent to the browser.
- Generated SQL is parsed before execution.
- Only approved read-only tables can be queried.
- Multiple SQL statements are rejected.
- DML and DDL are rejected.
- No fabricated fallback results are returned.
- Planner and Snowflake errors are surfaced explicitly.
- Query IDs support traceability.
- The frontend and backend have separate responsibilities.


17. POSSIBLE JUDGE QUESTIONS AND ANSWERS
-----------------------------------------

Q: What makes this different from a normal chatbot?

A: A normal chatbot may answer from language-model knowledge or produce an
unverified number. DataMind uses Gemma only to plan a query. Snowflake
computes the answer, and the user can inspect the SQL, rows, explanation,
warnings, and query ID.

Q: Does Gemma directly access Snowflake?

A: No. Gemma receives schema context and returns a structured plan. The
backend validates that plan and executes approved SQL using the Snowflake
connector.

Q: Can the model invent a column?

A: The planner receives the real schema, and the backend validates the
generated SQL against the configured table and column context. Invalid or
unauthorized SQL is rejected before execution.

Q: How do you prevent destructive queries?

A: SQLGlot parses the query. The validator permits one read-only SELECT-style
statement and rejects INSERT, UPDATE, DELETE, DROP, CREATE, ALTER, MERGE,
TRUNCATE, multiple statements, and unapproved tables.

Q: What happens when the question is unclear?

A: The planner returns clarification_required. The system asks a follow-up
question instead of guessing or executing unsafe SQL.

Q: What happens when the dataset cannot answer the question?

A: The planner returns unsupported, with an explanation. No Snowflake query is
executed.

Q: What happens when there are no matching records?

A: The SQL still executes successfully, but the response status is empty. The
UI clearly says no matching rows instead of treating it as a system failure.

Q: What happens if Gemma or Snowflake is unavailable?

A: The backend returns an explicit service error, normally HTTP 503. The
frontend shows the error and never fabricates a result.

Q: Why use Snowflake?

A: Snowflake provides managed cloud storage, SQL execution, scalable
analytics, schema discovery, and query IDs for traceability.

Q: Why use Gemma?

A: Gemma converts natural language into a structured, schema-aware query plan
while allowing the actual numerical computation to remain in Snowflake.

Q: Why not calculate the answer in Python?

A: The database is the source of truth. Snowflake is better suited to
filtering and aggregating the stored dataset, and keeping computation there
avoids discrepancies between backend code and database data.

Q: Why are charts created in the frontend?

A: Charts are presentation, not computation. The frontend can render a
lightweight chart from the returned JSON while keeping the original table and
SQL visible.

Q: Does every query produce a chart?

A: No. A chart appears only for a small, suitable category-plus-number result.
Single values, large raw tables, ambiguous requests, unsupported requests,
empty results, and errors remain text/table responses.

Q: How is the data ingested?

A: The CSV is validated, uploaded to a Snowflake stage with PUT, and loaded
with COPY INTO. The loaded row count is checked against the source dataset.

Q: Can you change datasets?

A: Yes. The dataset registry supports multiple configured datasets, including
the Bank Marketing dataset and Snowflake TPC-H. The active configuration
controls the schema prompt, database, schema, table allowlist, and SQL
validation.

Q: Is the query history stored in the cloud?

A: The current frontend stores the last 30 query entries in browser
localStorage. This is intentionally lightweight and avoids pretending that a
server-side multi-user history system exists.

Q: Is the login production authentication?

A: The current login is a demo/local frontend experience. Production
deployment would require adding a real identity provider and server-side
authorization.

Q: How do you handle missing values?

A: Snowflake returns the actual NULL values. The frontend displays them as an
em dash for readability, without replacing them with guessed values.

Q: What is the maximum result size?

A: The backend returns at most 500 rows and adds a warning when the result is
truncated.

Q: What happens if SQL syntax is invalid?

A: SQLGlot rejects it before Snowflake execution and the API returns an
explicit error.

Q: How do you know the result is real?

A: The response contains actual rows returned by Snowflake, the approved SQL,
and a Snowflake query ID. The frontend does not calculate or invent the
result.

Q: How would you improve this for production?

A:

- Add real user authentication and authorization.
- Add server-side audit logging.
- Add rate limiting and request quotas.
- Add async job handling for expensive queries.
- Add stronger semantic validation of numeric and date fields.
- Add automated evaluation sets for planner accuracy.
- Add dataset-level row and column security.
- Add persistent multi-user query history.
- Add monitoring and alerting.
- Add result exports with access controls.
